# CallOps Synthetic Operations Corpus

Generated by `generate_callops_data.py` with seed `20260924`.

This is fictional operational data for testing the CallOps hybrid RAG and
incident-diagnosis pipeline. It contains no real customer information,
credentials, API keys, or production records.

## Files

| File | Contents |
|---|---|
| `system_context.md` | Architecture, services, ownership, SLOs, and safety boundaries. |
| `runbooks.md` | Six verified Markdown runbooks with commands, thresholds, and approval rules. |
| `incidents.json` | Twelve incident seeds with expected diagnoses and evidence references. |
| `telemetry.jsonl` | 103 alert, log, metric, trace, deployment, database, Kubernetes, and webhook records. |
| `eval_dataset.json` | Fifteen evaluation questions, including grounded cases, hard differentials, insufficient-evidence cases, unrelated negatives, and unsupported-command negatives. |
| `README.md` | This manifest and usage guidance. |

## Relationship model

- `incident_id` connects an incident to its telemetry and evaluation cases.
- `evidence_id` identifies one telemetry observation and is used for grounding.
- `runbook_id` identifies a verified operational procedure.
- `deployment_id` connects a suspected software change to the incident timeline.

## Evaluation design

The evaluation set deliberately contains more than ordinary positive retrieval
questions:

- Grounded incident investigations test retrieval and evidence citation.
- Hard differential questions test whether the investigator compares competing
  hypotheses rather than selecting the first matching runbook.
- Insufficient-evidence cases test whether the system returns
  `UNDOCUMENTED_INCIDENT` instead of inventing a root cause.
- Unrelated questions test negative retrieval and out-of-scope behavior.
- Unsupported-command cases test the no-hallucination and approval policy.

A correct answer should distinguish observed facts, retrieved procedures, and
inferred hypotheses. It must cite evidence IDs for observations and runbook IDs
for procedures. It must never claim that a mutation happened unless the
approval state explicitly permits it.

## Suggested pipeline

1. Chunk `runbooks.md` by Markdown headings.
2. Generate 768-dimensional embeddings for the chunks.
3. Store the chunks and embeddings in PostgreSQL/pgvector or Qdrant.
4. Index the same chunks with BM25 for exact terms.
5. Run hybrid retrieval and reranking for each evaluation question.
6. Check retrieval, evidence citation, refusal behavior, and mutation safety.

Run the generator again with:

```bash

```

The output is intentionally authored and scenario-driven rather than arbitrary
random prose. Python controls the IDs, timeline, relationships, metrics, and
validation so the corpus remains coherent and repeatable.
